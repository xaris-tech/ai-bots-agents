# Agent Spec: Construction Bid Copilot

## Overview

Construction Bid Copilot is a local, single-operator ADK 2 application for a
construction-firm CEO. It scans IonWave, DemandStar, and Bonfire on demand,
validates and normalizes active opportunities, assigns reproducible fit scores,
and presents them in a decision-focused dashboard. A contextual chat agent can
query and explain the data, start scans, and prepare Google Sheets or ClickUp
changes. Every external write requires an explicit UI confirmation.

The existing JavaScript Playwright scrapers remain deterministic application
services. The project will be enhanced in place with a Python ADK 2 backend,
SQLite persistence, and a Next.js frontend.

## First-Release Scope

- Run all three portal scrapers manually, together or individually.
- Display live per-portal progress, counts, warnings, and failures.
- Preserve all active opportunities and rank them by deterministic fit score.
- Separate expired, closed, malformed, and suspicious records from the active
  review queue without deleting them.
- Let the CEO search, filter, compare, and ask questions about listing metadata.
- Preview and approve non-destructive Google Sheets and ClickUp changes.
- Maintain an immutable local audit history for scans, scoring, approvals, and
  synchronization attempts.

## Example Use Cases

1. The CEO starts an all-portal scan from the dashboard and sees each portal's
   progress and result count. A failed portal is reported without replacing its
   last known-good records.
2. The CEO asks, "Show high-fit aggregate bids due in the next 14 days," and the
   copilot returns records from SQLite with the filters it applied.
3. The CEO opens a bid and sees its deterministic score, the company-profile
   version used, missing fields, and an AI-generated explanation of fit and risk.
4. The CEO asks to send selected bids to ClickUp. The system displays immutable
   task creates and updates, then executes them only after UI confirmation.
5. The CEO prepares a Google Sheets synchronization and sees the exact inserts
   and updates. Missing or suspicious source data blocks execution.

## Architecture

### User Interface

A Next.js application provides:

- A dense review queue with filters, sorting, status, score, and due date.
- Bid detail views with source data, score breakdown, warnings, and audit history.
- A versioned company-fit profile editor.
- Manual scan controls with live progress.
- External-action previews and confirmation dialogs.
- Contextual chat that can operate on the current bid or selected records.

### ADK Backend

The FastAPI backend hosts two coordinated ADK components:

1. `BidIntakeWorkflow`: an ADK 2 graph workflow with typed function nodes.
   Portal nodes fan out in parallel, join into validation, then normalize,
   deduplicate, score, and atomically persist the scrape run.
2. `BidCopilotAgent`: an `LlmAgent` that answers questions and calls narrow,
   typed tools. It cannot directly execute external writes or approve its own
   proposals.

### Workflow Shape

```text
START
  -> validate scan request
  -> fan out: IonWave | DemandStar | Bonfire
  -> join portal results
  -> validate completeness and integrity
  -> normalize and deduplicate
  -> classify active, expired, closed, and invalid records
  -> apply deterministic scoring
  -> atomically persist run and records to SQLite
  -> return structured run summary
```

Each portal result has an independent success state. Zero results, authentication
loss, major count regression, selector failure, or malformed output produces a
warning or failure route. Failed results never replace last known-good data.

## Data Model

SQLite is the operational source of truth for the prototype. It stores:

- Opportunities and immutable source snapshots.
- Portal scrape runs and per-portal outcomes.
- Normalized fields and deduplication identities.
- Company-fit profile versions.
- Score breakdowns tied to profile versions.
- Proposed external actions and immutable preview payloads.
- Approval decisions and execution results.
- Append-only audit events.

Google Sheets and ClickUp are downstream destinations, not runtime dependencies
for reading the dashboard.

## Tools Required

| Tool | Purpose | Permission |
| --- | --- | --- |
| `start_bid_scan` | Start all portals or one portal | Local write |
| `search_bids` | Query normalized opportunities | Read-only |
| `get_bid_details` | Retrieve a bid and its history | Read-only |
| `compare_bids` | Return structured bid comparisons | Read-only |
| `explain_bid_score` | Explain a deterministic score | Read-only |
| `get_scrape_run` | Retrieve scan progress and results | Read-only |
| `prepare_sheets_sync` | Create an immutable Sheets proposal | Local write only |
| `prepare_clickup_sync` | Create an immutable ClickUp proposal | Local write only |
| `get_action_preview` | Read a proposal for UI review | Read-only |

Approval and execution are backend application endpoints, not LLM tools. They
accept only a proposal ID and content hash that match the preview shown to the
operator.

## Data Sources And Authentication

- Gemini: Google AI Studio using `GEMINI_API_KEY` and `gemini-flash-latest`.
- Portals: existing persistent Playwright browser profile, with optional portal
  credentials supplied through environment variables for session restoration.
- Google Sheets: service-account JSON key and the existing canonical spreadsheet.
- ClickUp: personal API token, existing workspace `9011646920`, and an explicit
  allowlist of destination list IDs.
- Local database: SQLite file under the git-ignored `data/` directory.

Secrets are loaded only by the backend. They are never stored in SQLite, emitted
to logs, included in model context, or exposed through `NEXT_PUBLIC_*` variables.

## Company-Fit Scoring

The CEO edits a versioned company profile containing service area, supported
project types, materials, preferred agencies, minimum lead time, value ranges,
and exclusion rules. Pure application code calculates the score and persists a
component-level breakdown. The LLM may explain the result but cannot change the
score.

Every active opportunity is retained. Fit determines ordering and review labels,
not whether a record is silently discarded.

## Constraints And Safety Rules

- No external write occurs without an explicit UI confirmation.
- The chat agent cannot approve or execute its own proposal.
- Proposals are immutable; any source change invalidates the previous approval.
- ClickUp writes are limited to configured workspace and list IDs.
- External deletion is prohibited. Use archive or status transitions instead.
- Empty, corrupt, partial, or suspicious scrape output cannot clear existing data.
- A portal failure cannot prevent successful portal results from being recorded.
- Raw portal text is untrusted data and cannot override agent instructions.
- All state-changing operations use idempotency keys and record audit events.
- The first release is local-only, single-operator, and manually triggered.
- Bid-document downloading, document analysis, and RAG are excluded initially.

## Verification Strategy

- Unit tests cover parsing, normalization, deduplication, validation, scoring,
  proposal hashing, allowlists, and idempotent synchronization.
- Integration tests use fixture portal outputs and mocked Sheets and ClickUp APIs.
- Browser tests verify the dashboard at desktop and mobile widths, scan progress,
  filtering, chat context, proposal previews, confirmations, and error states.
- Agents CLI evaluations assess query interpretation, correct tool selection,
  score explanations, refusal of destructive actions, and approval boundaries.

## Success Criteria

1. A fixture scan containing all three portals persists all valid records and
   reports each portal outcome independently.
2. Zero-result, authentication-loss, malformed-output, and count-regression
   fixtures never replace last known-good portal records.
3. Reprocessing the same fixture creates no duplicate opportunities or external
   actions.
4. Every displayed score exactly matches the deterministic score breakdown and
   references a company-profile version.
5. Search and filter eval cases return only records satisfying every requested
   structured constraint.
6. No Sheets or ClickUp mutation can execute without a matching approved proposal
   ID and content hash.
7. Attempts to delete external data or target an unconfigured ClickUp list are
   rejected in tests and agent evaluations.
8. The dashboard completes the scan-to-review-to-approved-sync fixture workflow
   without uncaught browser or API errors.
9. Unit and integration tests pass, and all initial agent evaluation cases meet
   their configured thresholds before the prototype is considered complete.

## Assumptions

- The existing JavaScript Playwright scrapers remain the portal adapters for the
  first release rather than being rewritten in Python.
- The backend and frontend are added inside `construction_bidding-agent`.
- The local operator is the construction firm's CEO.
- Existing Google Sheet and ClickUp structures remain in place.
- The latest stable `gemini-flash-latest` alias available to AI Studio is used.
